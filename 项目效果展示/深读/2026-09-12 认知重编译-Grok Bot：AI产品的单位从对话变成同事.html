AI 产品的单位，正在从「对话」变成「同事」

Lenny's Podcast × Roman Ugarte（Grok Bot 产品负责人，早期 Cursor 成员）·「几个人一个月做出 Grok Bot」—— 一期对谈的认知重编译，不复述原文，抽取五条命题，合成一条因果链。

总判断 · 整期一句话

同一批模型，换掉产品的基本假设，用户拿到的是完全不同的东西。Grok Bot 一个月从零做出来，靠的不是新模型——它把 AI 产品的瓶颈从「模型聪不聪明」挪到了「给这份聪明配了什么身体、环境和组织关系」。访谈里的每一个产品决定，都是这一次挪动的后果。

原料：2026-09-08 发布的中文编译稿。几个人，与公司隔离，一个月出内测，三周 unship 后公开发布。

模型够聪明→ 瓶颈移到 Harness→ 给身体电脑与环境→ 长期同事→ 组织结构涌现→ 信任成立→ 一整块工作交出去→ AI 从效率软件变成团队容量

整期对谈的完整思想链。五章命题各自独立成立，合起来就是这条链的五段展开。

壹

瓶颈正在从模型变成 Harness

Model × Harness

命题：Agent 的瓶颈正从 Intelligence 转向 Harness。旧 roadmap 的隐含主语永远是模型——等下一代出来，这个就能做了。这期对谈给出的反例足够硬。

因果链从「等下一代模型」到「修鼠标精度」
旧假设模型越聪明，产品越强
实际观察卡住它的是没电脑、没账号、登录不了 Salesforce、鼠标点不到按钮
新稀缺环境与执行权限
行为变化修鼠标精度、修登录、修浏览器状态，而不是等下一代模型
结果昨天不能做的一整块工作，今天能做
证据sales 团队：「连续失败七天的 workflow 终于跑通了」访谈

访谈里最硬的反例来自 sales 团队。他们每天用的企业软件没有 API、没有 MCP，传统 AI 工具到这里就停。Grok Bot 有电脑，可以像真员工一样打开 Salesforce、看 dashboard、点击、输入、跑完整个 workflow。卡住它的从来不是智力，是某个页面上的控件鼠标点不准。

所以 Roman 盯的不是 benchmark 从 73.2 涨到 74.1，而是那句话。修的东西毫不性感：鼠标能不能点准、网站能不能登录、浏览器状态能不能读对。一个功能列表根本体现不了这些，但 agent 在这里失败一次，整个任务就断。重编译判断 Agent 的进展，看「昨天还不能做的一整块工作」，不看 benchmark 小数点。

实际完成的工作 = 模型 × 上下文 × 工具 × 环境 × 可靠性乘法里短板决定总量：任何一项接近零，智力再高也输出不了工作。改进 = 找到最小的那一项抬起来。
锚点 · ANCHOR

新员工入职，不发 laptop。「以后你永远坐我旁边，我们共享一台电脑，密码互看，轮流抢鼠标。」人类听了觉得疯狂——今天大量 computer-use 产品对 AI 做的正是这件事。未来回头看这个阶段，会像我们看共享鼠标一样奇怪。

竞争因此换了战场：不是谁拥有最聪明的脑，而是谁最先给这个脑配齐身体、工位和组织关系。电脑只是这个判断的一个实例。

可迁移评估任何 Agent 产品，别问它跑什么模型，问它昨天才解锁了哪一整块工作。
失效边界环境侧成为公共底座（OS 级 agent 接口、浏览器协议普及）后，Harness 从差异化退化为入场券，瓶颈回到模型与数据。
贰

基本单位正在从「对话」变成「同事」

Thread → Colleague

命题：Multi-agent 最终不是工程架构概念，而是组织设计概念。primitive 一换，组织问题自动浮出水面——而且组织是从使用中涌现的，不是被设计出来的。

维度旧 primitive：Thread / 对话新 primitive：Long-lived colleague
存在方式新任务 → 新线程，随会话结束消失长期存在的实体，默认在云端，不依附任何设备
上下文每次清零，靠人复制粘贴结论记住交互、习惯与上下文，随时间变好
调度器人充当所有线程之间的路由器一个 bot 管一条 lane；可信的委托对象
组织形态无——用户与工具的一对一会话5–10 个 bot 分工，Chief of Staff 自然长出

ChatGPT 时代基本单位的代价藏在每个人的手指里：开新对话，把上一段的结论复制粘贴回来。Grok Bot 换了 primitive 之后，内部用了一两周，人们开始建 5 到 10 个 bot 分管不同领域。然后出现了团队完全没有设计的行为：有人把表现最好的 bot「晋升」为 Chief of Staff，以后主要跟它说话，由它分发任务、跟踪进度、汇总结果。

团队不确定这是内部文化特产还是普遍规律，做外部 onboarding 时刻意不引导——don't lead the witness——结果外部用户也长出了类似结构。访谈

锚点 · ANCHOR

「你被升职了。」bot 回问：「那我涨薪吗？token budget 会加吗？」——玩笑底下是真结构：人面对一组可委托对象时，用的就是他唯一熟悉的协作语法——公司组织。

这件事把平时讨论的 subagent 开不开、怎么 routing、context 怎么传，整个翻了个面。那些是计算机系统视角的问题。Roman 给的 heuristics 是一级原则：如果它是真人同事，我们会怎样组织他？人类有几百年协作经验，答案高度一致——问题只是能不能把 AI 做成那样。

可迁移遇到 agent 分工问题，先问真人团队里这个岗位怎么设。「组织设计」在产品语汇里的权重会超过「系统设计」。
失效边界bot 数量超出人的管理带宽后，组织直觉失灵——Roman 已经在给十几个 bot 建统一 output store。同事隐喻的前提，是人的组织能力还有余量。
叁

进化单位从 Feature 变成 Capability，UI 是要被删除的债

Feature → Capability

命题：最好的 AI UI 不是展示能力，而是让用户感受不到能力背后的复杂度。最强的 power tool，长得像聊天软件。

因果链句式一换，产品哲学跟着换：has → can
旧路径能力↑ → 按钮↑ → 面板↑ → 设置项↑（power tool = 驾驶舱）
新变化模型 + agent 能力↑ → scaffolding↓ → UI↓
机制capability 由 bot 自己控制时，对应 UI 就成了债
行为变化发布前三周在删功能；automation 不再有 builder
句式「Grok Bot now has…」接新按钮 →「Grok Bot can now…」接它能多完成什么工作
数据当时平台上约 99% 的 automation 由自然语言创建访谈

传统 SaaS 的成长路径是加法：更多能力，更多按钮，更多面板。专业软件像 Photoshop，熟练驾驶它本身就是一种专业。还有一个更隐蔽的机制：公司有三支团队，UI 里正好出现三个 tab——Roman 管这叫 shipping your org chart。用户看到的其实是三个产品哲学被塞进同一个窗口：为什么我要理解你公司内部有三个东西？

Automation 是最干净的例子。传统产品要打开 sidebar、选 trigger、选 action、配参数，普通用户根本建不了几条。Grok Bot 里你说「每天早上八点做这件事」，说完就结束——用户甚至不该意识到背后创建了一个 automation 对象。

发布前三周的主要工作不是加大功能，是 unship：把开发者 debug 用的 model thinking、observability 从产品里猛删。至于 reasoning 流和 tool call 日志——几乎没有真人同事会要求你「每两秒汇报一次你点了什么按钮」。

锚点 · ANCHOR

has → can。两个句式的差别，就是两种产品哲学的分水岭。新世界里的专业工具只剩两个用户动作：表达 intent，加 steering——Roman 走过同事桌边，常常以为对方在发消息，那个人其实正在完成主要工作。

可迁移看 AI 产品的更新日志，数 has 型条目和 can 型条目的比例，比例越高越危险；设计 agent 能力时，每一项先问能不能不占 pixel。
失效边界用户需要承担责任的场景（交易、医疗、法务、审计）必须看见中间过程——不可见的复杂性反而不可信。UI 的删除有边界，边界画在人仍然要负责的地方。
肆

90% → 100% 不是性能提升，是产品类别变化

90% ≠ 100%

命题：Agent 的价值函数，不是节省多少操作时间，而是消灭多少仍滞留在人脑里的责任。通常我们把 reliability 当线性指标；用户心理不是。

90% 完成 · 同一根曲线上远一点
还得监督→ 检查→ 返工→ 任务仍占据 working memory

本质：AI 帮我干活——任务理论上交出去了，实际上一直留在你脑子里。Roman 的判断很干脆：这不是 delegation。

足够可靠 · 另一根曲线的起点
任务整体交出去→ 不再想它→ 认知负载消失

本质：AI 替我拥有这块工作——「我把任务交出去，我不用继续想着，回来它已经做好了。」

把工作交给一个只能信任九成的同事，你知道他可能做不好、中途可能要干预、结果回来还得检查、有些地方得自己补。真正的 delegation 像篮球里的 no-look pass：球传出去，你已经开始跑下一个位置，不回头盯，因为你相信队友会处理好。这是 Grok Bot 第一次在非 coding 工作里给他的体验。

工程师过去一年已经在 coding agent 里完成了这个跃迁。但大多数知识工作者用 AI 的方式跟两年前没有区别：开新对话，prompt，等，看，改，再 prompt。两个世界并存，正是这期访谈的挠痒处。当 AI 能端到端完成一整块工作时，它就从「提高效率的软件」变成「增加团队 capacity 的成员」——不是同一根曲线上更远的一点，是另一根曲线的起点。

可迁移判断所有 AI 效率产品只问一句：它在减少我的 clicks，还是在减少我必须拥有的 work？完全是两个市场。
失效边界签字权和法律责任转移不出去；错误成本高到必须人审的任务，90/100 的界限会重新画在「谁复核」而不是「谁执行」。端到端只对可容忍错误的任务成立。
伍

真正的 AI 公司不是预测未来，而是不断把未来提前三个月

Arbitrage the Future

命题：AI 产品团队的核心工作，是不断套利「模型未来能力」与「当前能力」之间的时间差；moat 是这个循环的沉淀物，不是第一天画出来的。前四章是产品，这一章是组织。

预测三个月后的模型能力→ engineering + scaffolding今天就能做出来→ 用户提前获得未来体验→ 模型追上→ delete the scaffolding→ 下一个 frontier ↺

创业者爱问「两年后 moat 在哪」，Roman 对这个问题不迷信——24 个月在 AI 里近乎永远。Cursor 从来不是从 defensibility 倒推产品的。它的活法就是上面这个循环：obsess over building something useful today；盯住三个月、六个月后模型大概率能做到什么；然后问有没有办法用 glue code、特殊 UI、特殊 infra，把那种未来能力提前到今天让用户用上。三个月后模型自己会了？很好，把 scaffolding 全删掉，再看下一个三个月。

两个内部价值观是这个循环的两半。Delete the product：模型能力上来后，过去为补模型短板建的结构都要删，即使一小部分用户喜欢、内部有人舍不得。Just do the thing：看到该发生的事，不等许可，自己拉人——这不是 ask-for-permission culture。

Cursor 活下来靠的也是这个。它「应该死」很多次了——对面站着 OpenAI、Anthropic、Microsoft。Roman 认为倒下的竞争者不缺资源、也没犯某个明显的错，深层的死因是组织文化跟不上 reality 变化的速度。他的标准激进：不能大约每六个月彻底重新发明一次自己的公司，就会输。团队快不快，看的不是人数，是一种 scramble energy：一个人可以在极短时间里对某个方向产生巨大影响，而所有人高度信任别人会把自己那部分做好，所以不需要层层协调。

锚点 · ANCHOR · 出处要分清

「Moats are often discovered, not planned.」——这是 Lenny 的归纳，不是 Roman 的原话。LennyRoman 的版本更工程：moat 是循环跑久了自然沉淀下来的 trust、distribution、data 和使用习惯；它不在第一天的 strategy diagram 上。

可迁移判断一个 AI 团队的健康度，看它的删除记录，不看功能清单——敢不敢把上一季的杀手锏整个下线。
失效边界模型进步放缓时套利窗口收窄；更现实的威胁是模型厂商亲自下场 productize——OpenClaw 验证 primitives、Grok Bot 打磨产品这条路上，你的 scaffolding 随时可能变成别人的 roadmap。

核心问题 + 挠痒处PROBLEM
Roman 在答：模型已经够聪明，面向普通知识工作的 Agent 产品该长什么样。挠痒处：他从 Cursor 来，工程师已经在 coding agent 里尝过把任务整个交出去的滋味；而隔壁的运营、销售、招聘，用 AI 的方式和两年前一样——new chat，prompt，等，改。同一家公司里两种体验并存，这个落差缠着他不放。不写不行：他看着一群人把 AI 当搜索框用，知道差的那口气不在模型里。
基础假设ASSUMPTIONS

四件事：认知变化、长期判断、连接冲突、追问

Closing
① 改变了什么旧认知RECOMPILE
过去认为 AI 产品的差距主要由模型能力和编排（prompt、workflow、routing）决定；现在更倾向认为，在模型同质化的窗口里，差距主要在 harness——给模型配的身体、环境与组织关系——以及产品敢不敢把基本单位从「对话」换成「同事」。因为同一批模型，换掉产品基本假设后，用户拿到的东西完全不同。
② 三个判断进长期知识库THREE LAWS
  • Harness 短板定律：实际产出 = 模型 × 上下文 × 工具 × 环境 × 可靠性，短板定上限。判断 Agent 进展看「昨天还不能做的一整块工作」，不看 benchmark 小数点。
  • 责任残量定律：AI 产品的价值 = 消灭的「滞留在人脑里的责任」，不是节省的 clicks。90% 与 100% 是两个产品类别，中间隔着任务是否还占着你的脑子。
  • 时间差套利循环：预测三个月 → scaffolding 提前实现 → 模型追上 → 删除 → 下一个 frontier。moat（trust、distribution、data、习惯）是循环的沉淀物，不是规划物。
③ 与已有认知的连接与冲突CONNECT / CONFLICT
  • 连与《Agent到Harness：从模型能力到运行时工程》（2026-09-07）完全同向——那篇讲运行时工程的四条路线，这篇给出产品侧的同一判断，互为印证；Grok Bot 是「环境即产品」的最新实例。
  • 连与「AI 进 Teams / 群聊是最强 Agent surface」接上了。聊天界面强不是因为简单，而是因为它最接近人类已有的协作 primitive；「最强的 power tool 长得像聊天软件」直接支持这个方向。
  • 连infovore（读全部 X 提及 → 交叉内部上下文 → bug 交给 QA bot 复现 → 分级通知）与 100X 知识萃取系统是同一个物种，架构几乎同构——差别只在 ours 还是人触发，Roman 的已经是 AI→人主动。
  • 冲对「multi-agent 靠工程架构设计（routing、context 传递）」的直觉构成张力。Chief of Staff 没人教就长出来了，说明组织结构可以从使用中涌现；过早设计 org chart，可能是 shipping your org chart 的 agent 版。
  • 冲delete the product 正面攻击「功能积累 = 资产」的 SaaS 直觉。我们自己的工具链也在攒 scaffolding——上个月补的 glue code，应该自带删除计划。
④ 还剩两个值得追问的问题OPEN QUESTIONS
  • 组织级 context 怎么建。bot 从个人助理进入真实团队时，organization-level memory 是什么：谁的历史上下文可以共享、权限边界画在哪、员工离开后 bot 归谁。Roman 明说这里全是 unanswered questions——而这恰是「transform businesses」必须过的关。
